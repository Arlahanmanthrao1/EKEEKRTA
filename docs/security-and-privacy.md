# Security and privacy

This document describes implemented controls and unresolved risks. It is not a security certification.

## Trust boundaries

EKEEKRTA separates:

- the public browser application;
- the authenticated application API;
- the application database;
- the independent ERP service and database;
- external identity, video, mail, code-execution and messaging providers; and
- private recording/model workers.

Data crossing a boundary is validated, authenticated and minimized for that integration.

## Implemented controls

### Identity and authorization

- Passwords are hashed with bcrypt.
- Access tokens are signed and expire.
- Google sign-in validates an ID token but never creates an account or chooses a role.
- Protected routes use role dependencies plus institution/resource checks.
- Classroom moderator claims are generated by the backend.
- Platform-operator authentication is separate from institution login.

### Tenant isolation

- Institution ownership is stored on core records.
- Department, course, batch and enrollment scope narrows access further.
- Cross-tenant IDs are rejected even when a caller guesses a valid numeric ID.
- ERP configuration and synchronization events are institution-scoped.

### Secrets

- `.env`, private keys, local databases, recordings and private datasets are Git-ignored.
- Browser configuration contains no JaaS private key, database URL, ERP token, SMTP password or Google OAuth client secret.
- ERP API tokens are encrypted at rest in the application database and are not returned after storage.
- Production startup rejects a default/short `SECRET_KEY`, local SQLite and wildcard/non-HTTPS CORS configuration.

### Sensitive workflows

- Reset tokens are random, hashed, expiring and single-use.
- AI mutations require preview/confirmation and repeat authorization at execution.
- Quiz answers are omitted from student pre-submission payloads.
- ERP import requires preview and rejects privileged/conflicting records.
- Attendance and notification delivery use idempotent records to reduce duplicates.
- Parent WhatsApp messages require both a phone number and recorded consent.
- Recording uploads require an authorization/consent acknowledgement and remain outside public download routes.

## Privacy boundaries

- The ERP is the source of official academic identity/results when that connector is enabled.
- CGPA planning values are projections and do not modify official marks.
- Raw lecture transcripts and recordings are not made student-visible by default.
- Faculty must review lecture excerpts before publication.
- AI audit records avoid copying raw secrets, recordings and full transcripts.
- The repository intentionally contains no production credentials or seeded real institutional data.

## Known gaps before production

- Public institution registration needs verified domain/email ownership, approval and abuse controls.
- Formal threat modelling, penetration testing and dependency scanning are not complete.
- Alembic migrations and a rehearsed rollback process are needed.
- Centralized audit retention, monitoring, alerting and incident response are needed.
- Legal retention periods, deletion requests and data-processing agreements must be defined per institution.
- Accessibility and browser compatibility require formal testing.
- Self-hosted Jitsi requires secure JWT configuration, HTTPS, firewall review, capacity tests and monitoring.
- Code execution should use a dedicated isolated runner with strict network, CPU, memory and time limits.
- Real notification delivery requires an approved provider template and operational handling of opt-out/failure states.

## Responsible disclosure

Do not open a public issue containing credentials, personal data or an exploitable vulnerability. Contact the repository owner privately through the GitHub profile associated with this repository and provide the affected component, reproduction conditions and impact without including unrelated user data.

## Reviewer checklist

- Confirm `.env` and key files are untracked before every push.
- Use different secrets for local, preview and production environments.
- Grant the minimum scopes to Google and provider credentials.
- Back up and restore-test the target database before schema changes.
- Test an allowed and denied account for every new protected endpoint.
- Verify notification consent and deduplication using non-production recipients.
- Never claim meeting capacity without staged load tests and network measurements.
